# Недоступность сервера из облачного агента

Недоступность нужно описывать на той стадии, которую действительно наблюдает клиент. Облачный агент может получить только ошибку транспорта своего MCP-коннектора: запрос не дошел до обработчика инструмента или ответ не вернулся. В таком случае сервер не может добавить к уже потерянному ответу собственную диагностику. Сообщение `Transport send error` само по себе не устанавливает причину и не доказывает отсутствие эффекта записи.

| Что видит агент | Что установлено | Следующее действие |
|---|---|---|
| Инструмента нет в объявленном каталоге | В этой сессии инструмент пока не обнаружен | Использовать фактически доступный discovery API; после обращения к доступному каталогу ресурсов допустим один повтор поиска. Если инструмента снова нет, удержать только зависящие от него операции |
| `Transport send error`, `HTTP request failed` | Ошибка цепочки клиент → MCP или возврата ответа | Сохранить безопасную стадию, время и тип операции; для чтения применить ограниченную процедуру ниже |
| `connection_dns` или вложенная причина DNS | Ошибка разрешения имени в транспортной цепочке | Диагностировать DNS отдельно; по этой строке нельзя назначить виновным конкретный сервер или маршрутизатор |
| Timeout, включая долгий клиентский timeout | Ответ не получен в пределах бюджета | Записать измеренную длительность, стадию и число попыток, если известны; это не доказательство остановки обработчика |
| HTTP 401/403 | Требуется авторизация или право доступа | Проверить официальную настройку своего подключения; не повторять запрос по другим каналам в обход отказа |
| `startup.state=initializing` у графа | Инструменты видны, данные еще подготавливаются | Позже прочитать contract адресно; не перезапускать и не регистрировать сервер по кругу |
| `startup.state=failed` | Инициализация графа завершилась ошибкой | Отдельная диагностика; не выдавать старый архив за актуальный |
| `ready`, открытый TCP-порт или ответ 401 на пробу | Подтверждена только соответствующая стадия | Проверить аутентифицированное обнаружение и разрешенное чтение; эти признаки не заменяют успешный вызов |

Примеры сообщений ниже синтетические, без адресов серверов и реквизитов:

```text
Transport send error: HTTP request failed while sending a tools/call request
MCP HTTP headers helper timed out after 10 seconds
readReadiness.ready=false; blockerType=connection; reason=connection_dns
```

Формат оболочки зависит от MCP-клиента. Последняя строка — сокращенное представление нескольких полей Python toolkit, не обещание буквального JSON-ответа Node-сервера.

## Принятая процедура восстановления чтения

1. Отметить, был ли это read или write, время UTC, класс ошибки, измеренную длительность и доступные счетчики внутренних попыток. Не смешивать повтор агента с retry внутри HTTP-клиента. Не выводить URL с учетными данными, headers, cookies, payload и реальные ID.
2. При обычном сбое **чтения** выдержать паузу 10 минут, продолжая независимую работу. Это практическая пауза для оператора/планировщика, а не бесконечный retry и не доказательство причины. Более строгий действующий лимит попыток сохраняется. Отказ авторизации этой процедурой не обходится.
3. Один раз через то же настроенное подключение проверить статус и ограниченно прочитать существующий объект: сначала список с `top=1`, затем адресное чтение по возвращенному ключу, если статус не сделал нужную проверку сам. Не создавать и не проводить документы ради диагностики.
4. Если проверка снова не прошла, удержать зависимую работу и передать безопасную сводку для диагностики. Самовольно менять DNS, службу, клиент, credentials, тайм-ауты или регистрацию MCP не требуется.
5. Если чтение восстановилось, сообщить «чтение доступно в момент проверки». Причина прежнего сбоя остается неизвестной до отдельного доказательства; такой успех не закрывает проблему автоматически.

Node: используйте фактически обнаруженные `read.system.health_check`, `read.document.search_documents`, `read.document.get_document` согласно их текущей схеме (для поиска `limit=1`). `health_check` использует кэш metadata и сам по себе не доказывает свежую доступность чтения. Python: `onec83_connection_status(database="test")` отдельно возвращает `connected`, `metadataReady`, `readReadiness` и `writeReadiness`; проверка чтения выполняет ограниченный объектный GET. Успешная metadata или другая база не подтверждают доступность выбранной базы. Имена инструментов нужно проверить в discovery; разные реализации не имеют одинаковый wire-контракт.

Для графа проверяйте `contract → ready → overview → search(limit=1) → get → links → aggregate` в нужном объеме; ID берите из ответов, snapshot сохраняйте между шагами. `ready` не доказывает, что последующий поиск прошел. [Python toolkit](../contrib/python/README.md) содержит эти инструменты и локальную сводку безопасной телеметрии:

```bash
python -m onec_odata_mcp.log_summary PRIVATE.jsonl --output PRIVATE.summary.json
```

## Если ответ потерян при записи

Пауза не разрешает повторную запись. Сохраните `operation_id`/preview token и состояние журнала. При timeout, обрыве, пустом или несогласованном успешном ответе исход может быть неизвестен. Сначала выполните предусмотренную сервером сверку результата и readback. Новый идентификатор операции не делает повтор безопасным. Успешное повторное соединение также не доказывает, что предыдущий POST не выполнился.

Нативный сервер сохраняет механизм preview/confirm и journal/reconciliation; новая проверка УНП дополнительно удерживает неопределенное создание в пределах процесса. Общая уникальность между независимыми писателями требует ограничения на стороне 1С или согласованного единственного писателя. Перезапуск процесса сам по себе не является разрешением повторить операцию.

## Старт клиента и медленный helper

Ошибка helper при запуске MCP — отдельная стадия от выполнения инструмента. Легкий helper должен получать заголовки без импорта тяжелого SDK/графа, иметь ограниченное время и безопасные диагностические категории. Не печатайте bearer или JSON заголовков в отчетах. В Python toolkit эти части разделены и проверяются синтетическими тестами.

Если клиент поддерживает флаг необязательного подключения, например `required=false`, его осознанная настройка позволяет продолжать чаты, которым 1С не нужна. Она не исправляет handshake и не означает, что операции 1С доступны. Изменение работающей регистрации выполняют отдельно от диагностики. Не увеличивайте глобальные тайм-ауты и не меняйте константы SDK, чтобы скрыть неустановленную причину.

# Требования инструментов и диагностика OData

Установить или обновить MCP недостаточно для настройки 1С. Публикация OData и роли пользователя
настраиваются в самой базе. Провайдер может требовать точный перечень объектов и операций вместо
общего доступа ко всей конфигурации. Перечень MCP помогает подготовить такой запрос и увидеть,
что требуется новой версии или что перестало быть доступным позднее.

## Что происходит автоматически

После MCP `initialized` сервер в фоне проверяет дату сохранённого отчёта каждой настроенной базы. Если успешной проверки нет, прошло 24 часа или изменились требования/профиль, он загружает свежую `$metadata`. При повторном подключении с теми же требованиями в течение суток используется сохранённый отчёт с явным временем наблюдения.
Инициализация MCP не ждёт завершения проверки. Затем сервер проверяет имена, используемые поля,
ключи и объявленные функции относительно `src/capabilities/requirements.json`. При каждом старте
сохранённые отпечатки требований сравниваются с текущими: новый инструмент, новое поле или новая
операция существующего инструмента дают `newly_required` даже при неудачной связи с базой.

Начальный и ручной проходы выполняют не более **64 последовательных GET** по различным
опубликованным статическим целям чтения: `$top=0&$select=<один ключ>`. Это проверка принятия
ограниченного запроса, без запроса строк учёта. Один отказ не останавливает остальные цели.
Проба использует одну попытку штатного клиента, без повторов. Конечный сервер может всё равно
проверять права иначе для других строк/полей/фильтров — успех не доказывает доступ ко всем данным.
Никаких автоматических Create, PATCH, Post, Unpost, DeletionMark или DELETE нет.

По умолчанию каждые **86400000 мс (24 часа)** выполняется свежая проверка схемы и до **64 GET**.
Текущий перечень содержит 46 различных имён статических целей чтения, включая альтернативные
имена конфигураций; доступных выбранных целей обычно меньше. Они помещаются в один проход.
Цена прохода — один запрос metadata плюс до 64 GET, выполняемых последовательно. Следующая проверка назначается на оставшуюся часть 24 часов от успешной проверки, а затем раз в сутки. Время запросов добавляется к сроку получения результата; новый проход не начинается, пока предыдущий не завершён. Сбой сети или
медленная база не обещают соблюдения срока обнаружения отзыва доступа.

`ODATA_CAPABILITY_INTERVAL_MS` задаёт интервал 60000..86400000 мс.
`ODATA_CAPABILITY_PROBE_LIMIT` задаёт периодический бюджет 0..64; меньшее значение уменьшает
нагрузку и увеличивает срок обхода. При бюджете 3 и 46 доступных целях это до 16 интервалов плюс
время запросов. Значение 0 выключает только периодические GET; metadata продолжает проверяться,
начальный/ручной проходы сохраняют предел64. Для динамических объектов и функций, которые нельзя
безопасно вызвать без деловых аргументов, операция остаётся `unknown`.
`probeCoverage` показывает число целей, попытки последнего прохода и расчётный срок полного круга.

Изменения отправляются через поддержанный MCP logging notification и в stderr; stdout остаётся
транспортом JSON-RPC. Клиент MCP может скрывать logging notifications. Сводка в
`read.system.health_check` и сохранённая история доступны независимо от этого.

## Три инструмента

- `read.system.odata_requirements`: версия и требования всех инструментов; `tool` ограничивает
  результат одним именем. Для динамического инструмента задайте `entitySet` и при необходимости
  `fields` — только имена полей без значений. Проверяются выбранная схема, известные обязательные
  поля/ключи и объявления действий. Условия и составные выражения, которые невозможно разрешить
  без аргументов операции, остаются явно неразрешёнными.
- `read.system.odata_capabilities`: сохранённый отчёт без нового запроса к 1С. Повторное чтение отчёта не является новым наблюдением. Показывает текущую
  попытку, последнюю успешную схему с её версией требований/профилем, ограниченные наблюдения
  операций, события изменений, неизвестные свойства и запрос администратору.
- `read.system.odata_refresh`: принудительно обновляет metadata и выполняет начальный ограниченный
  проход чтения. Параллельные вызовы разделяют один проход. Запись в 1С не выполняется.

У всех трёх есть обычный параметр `database`. Проблема одной базы не выключает другие базы;
мониторинг не вводит общий запрет всех инструментов. Существующие проверки безопасности записи,
подтверждение, operationId, журнал, If-Match и другие ограничения продолжают действовать.

## Как понимать состояния

| Значение | Что установлено | Что не установлено |
|---|---|---|
| `published` | Требуемые поля/ключи/объявления найдены; типы проверены там, где перечень задаёт ожидаемый тип | Права чтения строк или записи, ограничения значений и бизнес-логика |
| `absent_from_accessible_metadata` | Имени нет в доступной схеме этого пользователя | Есть ли объект в конфигурации, скрыт ли он правами, требуется ли публикация |
| `schema_incompatible` | Есть точное расхождение используемых полей, ожидаемых типов или ключей | Можно ли исправить его публикацией; поддержку должен подтвердить администратор |
| `not_implemented` | Есть явно заданный факт администратора/поддержки для этой конфигурации и версии | Отсутствие объекта во всех конфигурациях страны или других версиях |
| `unknown` | Доказательств недостаточно или текущая проверка не завершилась успешно | Не считать успехом или отказом прав |

Отсутствующее объявление bound-функции не доказывает её отсутствия в 1С: схема может быть неполной.
Поля результата `Balance` проверяются на его типе результата, а не на корне регистра. Успешный GET
корня регистра никогда не становится свидетельством успешного вызова `Balance`.
Изменение типа используемого поля видно как `changed`, даже если перечень ещё не задаёт ожидаемый
тип и совместимость этого изменения неизвестна.

Операции имеют отдельное `effectiveStatus`: `observed_success`, `observed_denied` или `unknown`.
Наблюдение описывает один запрос, его время и область (`collection_query`, `one_record`,
`one_operation`). Через 48 часов оно становится `unknown`. Обычный согласованный запрос записи может
дать такое наблюдение; сервер не отправляет запись для получения свидетельства.

Явное сообщение 1С «Нарушение прав доступа» — наблюдённый отказ. Обычные401/403,404,500,
таймауты и сетевые ошибки сохраняются как неопределённость/недоступность.404 точной записи
не означает, что исчез весь объект. При потере metadata текущий отчёт показывает `unknown`,
а последняя успешная схема и время сохраняются отдельно. `READ_ONLY` и `WRITABLE` показывают
локальные предохранители MCP и никогда не выдаются за права роли1С.

## Профили и явные факты администратора

Без настройки используется `generic-1`, версии конфигурации и платформы — `unknown`.
Metadata сама по себе не определяет установленную версию конфигурации или платформы.
`generic` и `belarus` — версионные метки контекста, не автоматический перевод полей и не обещание
совместимости. Для плана счетов продолжают использоваться существующие `ODATA_ACCOUNTING_CONFIG`
и настройки каждой базы. Например, у банковского документа может быть `Контрагент_Key`, тогда как
конкретный инструмент создания отправляет `Контрагент` и `Контрагент_Type`: монитор показывает
расхождение условного поля и не подменяет контракт молча.

`ODATA_CAPABILITY_PROFILE` или `ODATA_DB_<ИМЯ>_CAPABILITY_PROFILE` принимает JSON. Синтетический
пример факта поддержки (вводите только подтверждённые сведения для своей базы):

```json
{
  "schemaVersion": 1,
  "revision": "by-2",
  "profile": "belarus",
  "configuration": "AccountingBY",
  "configurationVersion": "2.1.example",
  "platformVersion": "unknown",
  "source": "operator-record-42",
  "observedAt": "2026-10-01T00:00:00.000Z",
  "unsupported": [{
    "entitySet": "Document_СчетНаОплатуПоставщика",
    "configuration": "AccountingBY",
    "configurationVersion": "2.1.example",
    "source": "support-record-42",
    "observedAt": "2026-10-01T00:00:00.000Z"
  }]
}
```

Конфигурация/версия факта должны совпасть с профилем. Если версия неизвестна, укажите `unknown`
явно; такой факт не распространяется на будущие версии. Если текущая metadata показывает объект,
наблюдение схемы имеет приоритет, а `factConflict` требует уточнить устаревший факт.
В идентификаторы источников не помещайте URL, логины, токены или тексты бухгалтерских документов.

## Запрос администратору

`administratorRequest` содержит точные EntitySet, операции, поля/ключи и функции, которые относятся
к текущим диагностическим пробелам. Он различает отсутствие доступной схемы и доказанный отказ
операции. Условные и необязательные зависимости перечислены отдельно в требованиях инструмента:
они нужны лишь для выбранного сценария, не являются запросом общего доступа ко всей базе.

Если у вас есть административные права, откройте «Настройка стандартного интерфейса OData → Состав»
и проверьте нужные имена. Отдельно проверьте роли пользователя на чтение, создание, изменение,
проведение и отмену проведения именно нужных объектов. Если таких прав нет — передайте конкретный
список администратору/провайдеру. Отсутствующий в конфигурации объект нельзя создать настройкой
публикации; нужен ответ поддержки по конкретной конфигурации и версии. MCP состав публикации не меняет.

## Хранение и ограничения

`ODATA_CAPABILITY_STATE_DIR` по умолчанию — `~/.1c-odata-mcp/capabilities`. Для Docker подключите
постоянный закрытый том. Имя файла — SHA-256 нормализованного endpoint и principal. Пароль не входит
в идентичность; другой пользователь или база имеют отдельный baseline. Данные — только технические
имена/типы, классификации, времена, безопасный профиль и отпечатки требований. Нет URL, логинов,
паролей, ключей записей, значений, тел ответов или финансовых журналов. Каталог создаётся с 0700,
файлы с 0600, замена файла атомарная. При недоступном/повреждённом файле отчёт явно показывает
`persistence=unavailable`; нормальный запрос к 1С продолжает работать.

Хранятся последние 1000 событий и до 5000 текущих наблюдений операций. Это ограниченная история,
не бессрочный аудит. Остановка транспорта прекращает таймер; уже выполняющийся запрос может
закончиться, следующие пробы остановленного монитора не запускаются. Несколько процессов MCP,
использующих один файл endpoint/principal одновременно, не объединяют историю транзакционно:
используйте отдельный каталог состояния на процесс или один процесс для одной пары. Мониторинг
не даёт разрешения публикации, настройки ролей или изменения инфраструктуры.

## Для разработчика

Каждый зарегистрированный инструмент обязан иметь запись в `requirements.json`; новая регистрация
без записи отклоняется, тест сравнивает весь реестр с inventory. При изменении инструмента обновите
его поля, операции, обязательные/условные/необязательные зависимости, модель шапки/строк и revision.
Проверка отпечатков обнаруживает изменения существующей записи и добавление новой. Источник
перечня фиксируется `sourceVersion`/`sourceRef`; версия установленной 1С не выводится из этой версии.

`test/capabilities.test.ts` использует синтетические metadata/fetch и временные закрытые файлы.
`test/fake-1c.test.ts` прогоняет весь реестр на штатном снимке схемы. Живая база не требуется.
Полная проверка — `npm run check`; инструменты live-write для этой функциональности не запускать.
